# 批量生图：OpenAI 需求转配置与统一参考图改造方案

> 调查日期：2026-10-01。范围：本仓库静态源码的只读调查与改造方案；本文不代表功能已经上线。
> 已确认的产品范围：**本次只改造 OpenAI 批量生图，不改造 Gemini，不提供 nanobana 专用入口或专用逻辑。**
> 兼容约束：保持现有批量接口、认证方式、幂等方式、OpenAI 参数矩阵及上游请求方式不变；除非另行批准扩展后端契约。

## 1. 现版参数到底传到哪里

当前入口是 `/batch-image`，源码为 `frontend/src/views/user/BatchImageGuideView.vue`。原版表单中的参数先组装成批量接口请求，再由后端转换为 OpenAI 上游请求，链路如下：

```text
前端表单
  └─ POST /v1/images/batches
       ├─ 顶层：model / image_size / aspect_ratio / response_mime_type
       └─ items[]：custom_id / prompt / output_count / reference_images
            └─ 后端本地持久化、按 item 调度 worker
                 ├─ 无参考图：POST {OpenAI Base URL}/v1/images/generations
                 └─ 有参考图：POST {OpenAI Base URL}/v1/images/edits
```

### 1.1 页面参数 → 现有批量字段 → OpenAI 上游字段

这里区分**页面／批量接口字段**与**OpenAI 上游字段**。输入框和配置卡沿用现有 `image_size`、`aspect_ratio`，不增加独立的 `size`、`quality` 输入。

| 页面参数（改造后显示） | 原版前端状态 | `POST /v1/images/batches` 字段 | OpenAI 上游字段／实际行为 |
|---|---|---|---|
| API Key | `form.apiKeyId` | 不进入 JSON | 选中 Key 的 `key` 作为批量接口 `Authorization: Bearer ...` |
| `model` | `form.model` | 顶层 `model` | `model`；后端先按账号 `model_mapping` 映射 |
| `image_size`（尺寸档） | `form.imageSize` | 顶层 `image_size` | 与 `aspect_ratio` **共同**换算为上游 `size: "宽x高"` |
| `aspect_ratio`（宽高比） | `form.aspectRatio` | 顶层 `aspect_ratio` | 与 `image_size` **共同**换算为上游 `size: "宽x高"` |
| 输出格式 | `form.responseMimeType` | 顶层 `response_mime_type` | `output_format`，取 `png`／`jpeg`／`webp` |
| 任务名称 | `form.taskName` | 顶层 `task_name` | 本地任务属性，不传给上游 |
| `prompt` | `promptRows[].prompt` | `items[].prompt` | `prompt`，逐 item 传递 |
| Custom ID | `promptRows[].customId` | `items[].custom_id` | 本地关联／幂等标识，不作为上游请求体字段 |
| 每条生成数 | `promptRows[].outputCount` | `items[].output_count` | 后端展开为独立 item，每次上游请求 `n=1` |
| 参考图 | `promptRows[].reference_images` | `items[].reference_images` | `/v1/images/edits` 的重复 `image[]` 文件字段；批量只接受 inline `data` |

**映射关系：**`image_size` 的 `1K/2K/4K` 是分辨率档位，不是 OpenAI 的 `quality`；`aspect_ratio` 是宽高比。两者共同换算为上游 `size`（如 `1K + 1:1` → `1024x1024`）。本次保持两个原有字段名及后端映射逻辑不变，不添加 `quality`。

对应源码：

- 表单提交组装：`frontend/src/views/user/BatchImageGuideView.vue:1693-1712`
- HTTP 请求：`frontend/src/api/batchImage.ts:143-157`
- 后端 DTO：`backend/internal/service/batch_image_public.go:50-76`
- 网关路由：`backend/internal/server/routes/gateway.go:262-271`

### 1.2 后端传给 OpenAI 的真实字段

后端 OpenAI provider 位于 `backend/internal/service/batch_image_provider_openai.go`。它不是调用 OpenAI 官方 `/v1/batches`，而是本地保存批量任务后，逐条调用普通 Images API。

**无参考图：**

```json
{
  "model": "账号 model_mapping 映射后的模型名",
  "prompt": "当前 item 的 prompt",
  "n": 1,
  "output_format": "png | jpeg | webp",
  "size": "1024x1024"
}
```

请求：`POST {OpenAI Base URL}/v1/images/generations`。

**有参考图：**

请求：`POST {OpenAI Base URL}/v1/images/edits`，使用 `multipart/form-data`，文本字段为：

- `model`
- `prompt`
- `n=1`
- `output_format`
- `size`

参考图以重复的 `image[]` 文件字段上传。

对应源码：`backend/internal/service/batch_image_provider_openai.go:579-655`。

### 1.3 参数转换关系

| 批量接口字段 | OpenAI 上游字段 | 当前转换 |
|---|---|---|
| `model` | `model` | `account.GetMappedModel(input.Model)`，最终名称由账号映射决定 |
| `prompt` | `prompt` | 原样传递 |
| `output_count` | 无直接对应字段 | 后端复制/展开 item，每个上游请求固定 `n=1` |
| `image_size + aspect_ratio` | `size` | 例如 `1K + 1:1` → `1024x1024`，`4K + 16:9` → `3840x2160` |
| `response_mime_type` | `output_format` | `image/png` → `png`，`image/jpeg` → `jpeg`，`image/webp` → `webp` |
| `reference_images[].data` | `image[]` | 仅在 `/v1/images/edits` multipart 请求中上传 |
| `quality` | 无 | 当前批量 DTO、provider 和上游批量请求均未建模、未转发 |

特别注意：当前批量接口不接收或转发独立的 `quality`；本次不在输入框及配置卡提供该字段，也不把 `image_size` 解释为质量档位。

## 4. `llm to config` 输入和内部配置

### 4.1 用户输入格式

保持用户约定格式：

```text
prompt1;prompt2;......,image_size,aspect_ratio,model
```

- 使用英文分号 `;` 分割多个 prompt。
- 使用英文逗号 `,` 分割末尾参数槽位，依次为 `image_size`、`aspect_ratio`、`model`。
- `image_size` 和 `aspect_ratio` 分别校验为现有 OpenAI 矩阵中的尺寸档与宽高比组合；不另设 `size`、`quality` 槽位。
- `model` 为空时，内部使用哨兵值 `auto`，提交前解析为当前 OpenAI Key 返回的真实模型 ID。
- 保留三个英文逗号和三个参数槽位；槽位留空时分别使用 `1K`、`1:1`、`auto`，例如 `灯塔;港口,,,`。缺少槽位、额外英文逗号不自动猜测或补齐。
- 中文逗号 `，` 和分号 `；` 是提示词正文，不参与分割。英文分号始终表示下一条 prompt；需要字面英文分隔符时，在转换后的卡片中编辑。
- 解析错误指出字段或 prompt 序号及原输入中的位置（从 1 开始，按 Unicode 码点计数）；每条 prompt 按 UTF-8 校验 8000 字节上限。

示例：

```text
红色陶瓷杯;蓝色陶瓷杯,1K,1:1,
```

解析为两张配置卡：

```text
prompt: 红色陶瓷杯 / 蓝色陶瓷杯
image_size: 1K
aspect_ratio: 1:1
model: auto（提交前解析实际模型）
```

如果 prompt 本身包含作为分隔符的英文 `;` 或末尾英文 `,`，当前语法无法无歧义解析。首次实施不自行增加转义规则，而是显示精确错误并要求用户在卡片中修正。

### 4.2 内部 config 不等于后端请求

建议的前端内部结构：

```ts
{
  localId: string,
  prompt: string,
  image_size: '1K' | '2K' | '4K',
  aspect_ratio: string,
  model: string, // 'auto' 仅是 UI 哨兵值
  output_count: number,
  referenceMode: 'shared' | 'perItem',
  reference_images: ReferenceImage[],
  validationErrors: string[],
}
```

提交前转换为：

```ts
{
  model,
  task_name,
  image_size,
  aspect_ratio,
  response_mime_type,
  items: [{ custom_id, prompt, output_count, reference_images }],
}
```

提交时直接将卡片的 `image_size`、`aspect_ratio` 写入批量请求的同名顶层字段；不得把上游 `size`、`quality`、`model: 'auto'` 或内部 `referenceMode` 发送给 `/v1/images/batches`。

### 4.3 现有尺寸字段的校验与映射

1. 分别校验 `image_size`、`aspect_ratio`，只允许现有 OpenAI 参数矩阵支持的组合。
2. 缺省值沿用现有页面默认值；卡片编辑直接更新两个原字段，不产生额外的 `size`／`quality` 配置项。
3. 提交前按两个原字段连同模型等顶层参数分组；上游 `size` 仍由后端现有逻辑换算，可在页面只读显示像素尺寸供核对。

```text
结果: 成功图片只收录一次；失败项不伪装为已生成图片。
```

校验失败需给出 prompt 序号、字段名、当前位置与修复方法；不要自动猜测分隔符。当前语法无法无歧义表达 prompt 中作为分隔符的英文 `;` 或末尾英文 `,`，应明确提示而非静默误拆。多批次时显示“提交集合（N 个子批次）”而非虚构一个后端 batch；单批继续沿用原下载入口，多批才执行前端合并。

### 5.6 页面字段和能力约束

- 参数矩阵只读复用 `frontend/src/utils/batchImage.ts` 中现有 OpenAI `1K/2K/4K × 8` 组合；用 `image_size` 与 `aspect_ratio` 作两轴，像素 `size` 仅供阅读，不提供 `size`／`quality` 编辑项。
- `API Key` 从现有列表选且限定 OpenAI；`model` 的下拉选项只来自当前 Key 可用模型；`auto` 必须在提交前解析为实际模型 ID。当前 Key 无模型、能力加载失败或不满足矩阵时禁用提交。
- `response_mime_type` 沿用原有全局输出格式控件；若将来需要逐卡不同格式，应另评估交互和分组范围，当前原型不增加该能力。`task_name`、`custom_id`、`output_count` 保留现有默认和校验约束。
- 每卡展示“用户配置”和“实际发送预览”：卡片的 `image_size`、`aspect_ratio` 发送到批量接口**同名顶层字段**；不同规格的卡片分组提交。上游 `size` 由后端换算，绝不把 `model=auto` 或 UI 内部字段直接发给服务端。
- 输入/卡片/一致性引用区必须能指出失败原因、重新解析覆盖警告与请求容量限制；界面中的示例模型与像素值不得误示为该 Key 已获授权。

### 5.7 按钮职责与直接生成交互（本次确认版）

本页面明确采用“左侧转换、右侧提交并直接开始生成”的单向交互，不把两个动作混成一个按钮：

```text
左侧：需求输入区                              右侧：配置区
┌──────────────────────────────┐             ┌──────────────────────────────┐
│ 输入：prompt1;prompt2,1K,1:1, │             │ 转换前：不显示配置卡            │
│                              │             │                              │
│ [转换]                         │             │                              │
│                              │             │                              │
│ 点击「转换」                   │             │ 转换成功后显示配置卡            │
│   └─ 解析分隔符和参数           │ ─────────▶ │ 可折叠、可修改、逐卡校验          │
│   └─ 生成 config 草稿           │             │                              │
│   └─ 不调用生图接口             │             │ 右侧底部固定操作栏：             │
└──────────────────────────────┘             │ [提交并开始生成]                 │
                                             └──────────────────────────────┘
                                                        │
                                                        ▼
                                           点击后直接提交并启动生成任务
                                           不再弹出二次“确认生成”步骤
```

- **「转换」只负责输入转换**：读取左侧文本、校验 `prompt`／`image_size`／`aspect_ratio`／`model`，并在右侧生成或更新配置卡；点击后不得创建 batch、扣费、上传生成请求或开始轮询。
- **「提交并开始生成」只负责执行**：读取右侧当前有效配置卡，先完成必要的能力和容量校验，随后直接调用既有 `POST /v1/images/batches`；多规格时按分组连续创建原有子批次，并立即进入已有的排队／生成状态展示。
- 转换失败时右侧不生成半成品卡片，底部「提交并开始生成」保持禁用；转换成功但某张卡被编辑为无效时，仅显示错误卡片并保持提交禁用。
- 左侧文本为空时不显示配置区；只有点击「转换」且转换成功后，右侧才渲染配置卡和底部提交操作栏。
- 提交按钮应明确表达副作用：使用「提交并开始生成」，不使用含义不清的「确定」或「保存」。点击后按钮进入“提交中／已开始生成”状态，防止重复点击；失败时仅允许按提交集合重试未成功的子批次。

```text
[空输入]
    │ 输入文本
```

## 6. OpenAI 提交流程

### 6.1 同规格配置

若所有卡片的 `model`、`image_size`、`aspect_ratio`、`response_mime_type` 相同，继续调用一次原有：

```text
POST /v1/images/batches
Authorization: Bearer <所选 API Key>
Content-Type: application/json
Idempotency-Key: <独立幂等键>
```

请求体仍只包含原有顶层字段和 `items[]`。

### 6.2 不同规格配置

现有后端一个 batch 只能统一顶层规格。若卡片之间规格不同，不能把不同值塞进同一请求；前端应按以下键分组：

```text
API Key + OpenAI provider + model + image_size + aspect_ratio + response_mime_type
```

每组按原接口提交一个或多个批次：

- 每个批次仍调用原有 `POST /v1/images/batches`。
- 每批使用独立 `Idempotency-Key`。
- 每个批次只携带属于该组的 `items[]`。
- 页面维护一个“提交集合”，记录组、batch ID 与卡片 `localId/custom_id` 的映射。
- 某组失败时，只重试未提交组，不重新提交已被服务端接受的组。
- 页面层聚合排队、成功、失败和费用，但不把多个后端 batch 伪装成一个 batch。

### 6.3 一致性参考图

开启一致性后：

- 前端读取一张统一参考图并校验 PNG/JPEG/WebP、大小和读取结果。
- 每个实际提交的 `items[i].reference_images` 都放入同一张图的合规 inline `data`。
- OpenAI provider 会将有参考图的 item 发往 `/v1/images/edits`，字段名为 `image[]`。
- 必须按 item 数量估算 Base64/请求体膨胀及后端批次内联上限；超限时分组或阻止提交，不能漏传参考图。
- 页面原样显示提示：**“需保持一致性建议使用 `-gpt-image2.5-sunburst`”**。
- 该提示不是自动切模指令；实际模型仍由当前 Key 的模型列表决定。

## 7. ZIP 导出

- 单个 batch 继续调用现有 `GET /v1/images/batches/{id}/download`，因为服务端已经返回 ZIP。
- 多规格分组产生多个 batch 时，页面等待所有子批次进入终态，分别下载原 ZIP，再在浏览器端合并为一个总 ZIP。
- 总 ZIP 只包含实际成功且下载校验通过的图片，并建议包含：
  - `images/<顺序号>-<安全化custom_id>-<index>.<ext>`
  - `manifest.json`：卡片、实际配置、batch ID、文件映射
  - `errors.json`：失败项、未生成项、过期项或下载失败项
- 发生失败时，按钮文案必须明确为“导出已成功生成图片”；不得宣称失败项也已包含。
- 必须设置浏览器内存、总大小和文件数量上限，避免静默生成不完整 ZIP。
- 现有前端未直接声明 ZIP 合并依赖，实施阶段需选择并审计一个受控 ZIP 库。

## 9. 验收用例

1. `红色陶瓷杯;蓝色陶瓷杯,1K,1:1,` 生成两张配置卡，分别含 `image_size=1K`、`aspect_ratio=1:1`；`model=auto` 在当前 Key 模型列表中解析为实际模型。
2. 上方矩阵只展示现有 OpenAI `1K/2K/4K × 8` 组合，不出现 Gemini 或 nanobana 专用矩阵。
3. 同规格卡片只产生一次原有 `POST /v1/images/batches`；不同规格卡片按组产生多个原有 POST。
4. 网络请求中只能看到 `model`、`task_name`、`image_size`、`aspect_ratio`、`response_mime_type`、`items[]` 等既有批量字段；页面输入及配置卡不出现 `size`、`quality` 编辑项。
5. 后端 OpenAI 请求验证：无参考图使用 `/v1/images/generations`，请求字段为 `model/prompt/n=1/output_format/size`；有参考图使用 `/v1/images/edits`，参考图字段为 `image[]`。
6. 一致性开启且无统一参考图不能提交；每个 item 都带同一张参考图；不支持的模型不能退化为无参考图请求。
7. 单批下载继续获得原 ZIP；多批仅在所有结果明确后合并总 ZIP，成功图片恰好一次，失败项写入 `errors.json`。
8. 运行相关前端测试、新增解析器和 ZIP 测试，并执行 `pnpm --dir frontend typecheck`；后端回归 OpenAI batch provider、提交和下载测试。

## 10. 风险与待决策项

- **`image_size` 不等于 `quality`。** 两个原字段共同映射上游 `size`；当前批量接口不支持独立质量控制，本次不承诺该能力。
- **`model=auto` 不能直接提交。** 后端的价格预留和 provider 校验要求实际模型，必须先从当前 Key 的模型列表解析。
- **统一参考图会放大传输体积。** 每个 item 都重复携带同一图片，需提前检查单批总内联限制。
- **多规格分组会增加请求数。** 需要页面级集合状态，且部分提交失败时不能整体盲目重试。
- **OpenAI 模型可用性不是由提示文案保证。** `-gpt-image2.5-sunburst` 只有在当前 Key 返回并允许调度时才可使用。
- **nanobana 不作为本次产品能力。** 即使账号映射中存在同名 alias，也不新增针对它的兼容承诺。
