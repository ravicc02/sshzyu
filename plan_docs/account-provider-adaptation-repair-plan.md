# 账号管理 OpenCode / MiniMax 适配补齐方案

日期：2026-10-06  
状态：待确认，本文不代表功能已实施  
范围：补齐官方基线已有的账号添加、编辑能力，保留本站定制逻辑。

## 1. 背景与已核验结论

用户反馈：账号管理可以按 OpenCode 筛选，但添加账号时无法选择 OpenCode。

本次对照对象是仓库记录的官方 **v0.2.13**，提交
`3040209f205472038c1ba745a1bedd2edd9053b1`，不是未经核实的官方最新开发分支。

已核验：

- `frontend/src/constants/platforms.ts` 的统一平台目录包含 `opencode_go`、`minimax`，筛选组件使用该目录。
- 本地 `CreateAccountModal.vue` 的平台按钮为手写列表，缺少 OpenCode 和 MiniMax。
- 官方基线的添加弹窗已有这两类平台入口，OpenCode 已有 Go / Zen 模式。
- 官方基线的编辑弹窗已有 OpenCode 模式配置，本地编辑弹窗未接入 OpenCode。
- 本地 `credentialsBuilder.ts` 已包含 OpenCode 默认地址、Go / Zen 默认协议规则等辅助代码，后端账号校验及业务代码也已有相关支持。
- 对照整合提交 `351827563530519f4f3b83b37268240220e7f08b` 与官方基线，添加弹窗未保留上述官方功能。

结论：这是三方整合后前端功能链路不完整，不是仅添加一个按钮就能解决的问题。现有证据不能证明当时具体的冲突处理过程，也不能把测试通过等同于新增平台流程完整。

## 2. 目标与边界

### 本次目标

1. OpenCode、MiniMax 均可从添加入口选择，按官方基线支持的账号方式保存。
2. OpenCode Go / Zen 模式、API Key、默认地址、协议规则能够正确联动。
3. 已有账号可编辑并正确回填，不因编辑丢失凭证配置。
4. 保留本站定制平台、账号配置与风控逻辑，不整文件覆盖官方源码。
5. 补充平台入口与凭证流程测试，防止下一次合并再次出现“筛选有、添加无”。

### 不做的事项

- 不升级官方基线，不自动拉入 main 的新功能。
- 不修改生产数据、迁移、发布版本号或部署配置。
- 不创建真实上游账号、不消耗上游额度作为默认验收手段。
- 不因本次修复重做整个账号管理界面。
- 不改动本地未归属文档和 UI 构建产物的 Git 跟踪策略。

## 3. 实施前核对

实施时重新阅读 `AGENTS.md`，检查工作区状态及适用的目录级规范。

以官方基线和本地文件做逐段对比，先列出能力矩阵：

| 项目 | 核对内容 |
| --- | --- |
| 添加入口 | OpenCode、MiniMax 可选；切换后账号方式正确 |
| OpenCode 模式 | Go / Zen 默认值、切换行为、持久化字段 |
| 协议 | 官方允许的协议选项、模型匹配规则、回退协议 |
| 默认地址 | 与 `credentialsBuilder.ts` 一致；自定义地址不被无故覆盖 |
| MiniMax | 官方允许的账号模式、协议、预设地址、模型映射 |
| 编辑 | 旧账号回填、缺省字段兼容、保存后字段保留 |
| 后端契约 | 创建和更新 DTO、校验、凭证字段及路由解释一致 |
| 定制功能 | TypeSafe / Jev、现有平台、分组、代理及其他定制配置不退化 |

后端已有支持不等于所有前端 payload 均已验证；必须核对实际创建、更新契约。发现后端缺陷时记录证据，再决定是否纳入修复，不能盲目改后端。

## 4. 前端修改设计

### 4.1 添加账号

修改 `frontend/src/components/account/CreateAccountModal.vue`：

- 补齐 OpenCode、MiniMax 平台选择入口，沿用现有按钮风格。
- 从官方基线逐段迁入所需状态、计算属性、模式选择和提交分支。
- OpenCode 使用 `opencode_go` 作为平台标识，通过模式字段区分 Go / Zen；不得新增未经后端支持的 `opencode_zen` 平台。
- 复用 `credentialsBuilder.ts` 的地址和协议辅助函数以及现有 `OpenCodeGoProtocolRulesEditor.vue`，不复制第二套默认规则。
- 切换平台、模式、协议时清除不适用的表单状态，遵循官方行为处理默认地址；保留有效用户自定义配置。
- 校验空 Key、无效规则等情况；提交 payload 不携带其他平台的残留字段。

### 4.2 编辑账号

修改 `frontend/src/components/account/EditAccountModal.vue`：

- 补齐 OpenCode Go / Zen 模式、地址和协议配置的回填与保存。
- 对 MiniMax 做同等逐项核对并补齐缺失能力。
- 没有显式模式字段的旧账号，使用现有辅助函数与官方基线的兼容规则，不自行猜测新的默认值。
- 协议规则恢复默认值应随当前 Go / Zen 模式变化。
- 编辑时保留未知或与本次无关的既有凭证字段，遵循现有凭证合并语义；不得因为表单未展示就删除。

### 4.3 平台目录与能力约束

问题根源之一是筛选目录与添加入口各自维护。建议：

- 尽量让添加入口从统一平台目录派生，再按显式能力配置组织布局。
- 若为了控制改动范围暂时保留手写按钮，必须增加“目录平台与添加入口一致”的回归测试。
- 筛选支持与手动创建支持不应被默认视为等价；确实只读或不可创建的平台，需在能力配置中明确原因并有测试，而不是静默漏掉。
- 不为解决两个平台引入复杂插件体系。

## 5. 回归测试与验收

先补失败测试，再修改实现；沿用仓库现有测试工具和相邻测试结构。

### 5.1 组件与凭证测试

在 `frontend/src/components/account/__tests__/` 以及现有凭证辅助测试位置覆盖：

1. OpenCode、MiniMax 添加入口均可见且可选。
2. OpenCode Go / Zen 分别生成正确的平台、模式、地址与协议规则。
3. 模式切换、规则恢复默认、自定义规则及回退协议能正确保存。
4. MiniMax 官方支持的模式与协议组合能生成正确 payload。
5. 从其他平台切入、切出后，无残留错误字段和失效账号类型。
6. Go / Zen 及旧账号的编辑回填与保存往返一致。
7. 不修改 Key 时遵循现有保存语义，不清空已有凭证。
8. 编辑不会删除无关既有凭证字段。
9. TypeSafe / Jev 和现有主要平台的定制流程不退化。
10. 统一目录与实际添加入口的覆盖关系有自动断言。

### 5.2 本地浏览器验证

构建后通过本地站点 `http://127.0.0.1:8080/` 验证：

- 打开账号管理和添加弹窗，确认两个入口及其配置显示。
- 按用户顺序切换平台、模式、协议，检查文案、默认值、必填校验和布局。
- 桌面及移动宽度均无按钮溢出或不可访问的配置。
- 创建、编辑流程优先通过 mock 或隔离测试环境验证；不得默认向当前本地数据库写入测试账号。
- 若需要当前本地数据库真实保存测试，先取得单独授权，使用非生产凭证，并明确测试数据处理方式。

### 5.3 验收门槛

- 新增定向测试、现有相关测试、typecheck、相关文件 lint 和构建均通过。
- PR 的后端、前端及其他适用必需检查全部通过。
- 对每个平台给出“添加 → payload → 编辑回填 → 保存”的验证结果，不只报告测试总数。
- 默认不调用付费上游；如需真实上游验证，另行取得账号与费用授权。

## 6. 官方整合防遗漏机制

在 `plan_docs/official-upstream-versioning-workflow.md` 补充前端整合检查项：

- 逐项核对新增平台是否贯通筛选、添加、编辑、凭证、分组和路由；允许的差异必须显式记录。
- 对冲突文件不仅做编译验证，还要检查官方新增状态、事件、提交分支是否遗漏。
- 按新增能力建立测试清单，不能用“已有全量测试通过”替代新增流程测试。
- 保留定制差异说明，避免后续整文件选取 ours/theirs 导致功能丢失。

本次只要求补充与平台整合有关的轻量检查和测试，不扩大为全仓库自动功能比较系统。

## 7. 实施顺序与交付

1. 官方基线对照，形成平台能力及定制差异清单。
2. 新增失败测试，锁定 OpenCode / MiniMax 添加和编辑缺口。
3. 补齐添加、编辑和凭证联动，复用现有辅助代码。
4. 验证定制平台回归、运行检查、完成本地浏览器只读验收。
5. 更新官方整合规范，输出改动清单及测试证据。
