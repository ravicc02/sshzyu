# 官方 Sub2API 上游同步与本地定制版本治理方案

> 状态：2026-10-01 开始配置；`upstream` 已配置、`upstream-baseline.json` 与本机 `pre-push` 门禁已落地。未进行新的上游合并、线上部署或历史 migration 验收。
> 适用仓库：`sshzy` 统一仓库
> 官方上游：`Wei-Shaw/sub2api`
> 更新日期：2026-09-30

## 1. 目的与原则

本文件记录官方 Sub2API 源码与 `sshzy` 本地定制版的协作、版本和发布流程建议。目标是在吸收官方更新的同时保留本地功能，并在对外推送前发现官方新 release。

基本原则：

1. 官方仓库是上游源，`sshzy` 仓库是包含本地定制与统一项目结构的协作仓库，两者不能混为一谈。
2. 以官方稳定版 Release 对应的 tag 作为上游基线；不能仅凭镜像更新时间、默认分支提交或 `VERSION` 文件推断官方版本。
3. 合并是增量集成，不是用官方源码覆盖本地定制。
4. 版本号同时表达官方基线与本地修订，避免本地定制构建与官方原版发生版本碰撞。
5. 推送前若无法确认官方 release 状态，检查结果应为“未知”，不能当作“没有更新”。
6. 数据库 migration 已发布/应用后必须保持不可变；不得为解决编号冲突而直接改名、改内容或重编号已应用 migration。

## 2. 仓库与上游身份

- `origin` 指向 `sshzy` 协作仓库，用于本项目日常协作与推送。
- 官方上游仓库固定为 `Wei-Shaw/sub2api`。建议在本地 Git 配置中使用 remote 名称 `upstream`。
- 配置 `upstream` 属于一次性环境准备；执行前先检查现有 remote，避免重复添加或覆盖已有配置。
- 官方稳定版本以官方 GitHub Releases 页面及其对应 tag 为准：<https://github.com/Wei-Shaw/sub2api/releases>。
- 如需记录具体上游来源，保存 release tag、对应 commit SHA、release URL 和检查日期；不要只记录可变的分支名。

当前仓库已配置 `upstream`；不要重复执行下述 `git remote add`。其他机器先检查现有 remote 再决定是否配置。建议的一次性配置命令（执行前检查 `git remote -v`）：

```bash
git remote add upstream https://github.com/Wei-Shaw/sub2api.git
git fetch upstream --tags
```

> 当前仓库包含整合后的前后端、文档、部署配置和本地定制，不应假设可以直接将官方 monorepo 分支 merge 到整个仓库。上游源码应按受控的三方比较与移植流程集成。

## 3. 版本号规则

### 3.1 格式

- 官方基线版本：`X.Y.Z`，例如 `0.2.11`。
- 本地定制构建版本：`X.Y.Z-rN`，例如 `0.2.11-r6`。
- `X.Y.Z` 必须对应已经核实的官方稳定版 Release/tag；禁止把尚未发布的版本号用作本地正式版本前缀。
- `N` 是当前官方基线下递增且不可复用的本地修订号。
- 在同一官方基线下发布本地修改时，只递增 `rN`，不得修改 `X.Y.Z`。
- 合并新的官方基线后，基线改为新的官方版本，本地修订号从 `r1` 重新开始。例如：`0.2.11-r6` 合并官方 `0.2.12` 后，新的本地定制版本为 `0.2.12-r1`。
- 不得在本地定制提交上创建或使用形如 `vX.Y.Z` 的官方 tag。

### 3.2 版本的展示与追溯

版本展示分为用户展示和运维标识：

| 场景 | 建议展示 | 示例 |
|---|---|---|
| 产品界面面向普通用户 | 官方基线版本 | `0.2.12` |
| 二进制 `--version`、Docker tag、部署日志、运维诊断 | 完整本地构建版本 | `0.2.12-r1` |
| 发布记录/部署记录 | 官方基线、完整构建版本、Git SHA、上游 tag/commit | `upstream v0.2.12 / build 0.2.12-r1 / SHA <commit>` |

产品界面可按产品需求只显示官方版本，但任何可用于排障、回滚或审计的记录必须保留 `-rN` 与 Git SHA。若把 `--version`、Docker tag 等技术标识也隐藏 `-rN`，会导致官方原版和本地定制版难以区分，故不推荐。

### 3.3 构建要求

- 正式发布构建必须显式使用并验证完整本地版本号 `X.Y.Z-rN`，避免构建脚本从 tag 自动推导时意外覆盖本地修订号。
- 仓库根 `Dockerfile` 与 `backend/Dockerfile` 的版本注入行为如有差异，应在实际发布前统一或明确唯一正式构建入口；不得让不同构建入口产出不同版本标识。
- 发布记录应核对版本文件、构建参数、二进制 `--version`、Docker 镜像 tag 与 Git SHA，确保彼此一致。

## 4. 每次 push 前的官方 Release 检查

每次向 `origin` 推送前，执行以下检查：

1. 检查当前分支、工作区状态、待推送提交和当前版本号。
2. 获取官方最新稳定 Release/tag，并与仓库记录的当前上游基线比较。
3. 使用 tag/commit 确认版本，而非仅看镜像发布时间或默认分支最新提交。
4. 记录检查时间、当前上游基线、最新官方 tag、release URL 与对应 commit SHA。

检查结果处理：

- **没有比当前基线更新的官方稳定 Release**：继续常规测试与推送流程。
- **发现更新的官方稳定 Release**：停止 push；向用户汇报当前基线、新 release 版本、发布时间、链接和初步变更范围，并询问是否需要先合并。
- **无法连接 GitHub、无法 fetch、upstream 未配置、release 状态无法确认**：标记为“未知”，暂停 push 并报告阻塞原因；不得把失败解释成“没有新版本”。
- 未获得用户明确确认时，不自动合并/rebase、不覆盖本地定制、不推送受影响代码。

此规则要求的是“每次 push 前检查并在有更新时询问”，不要求每次都自动升级。

## 5. 用户确认合并新 Release 后的流程

### 5.1 固化与基线确认

1. 检查工作区是否干净；未提交改动先识别归属，不得静默覆盖或丢弃。
2. 记录当前 `HEAD`、当前官方基线 tag/commit、本地版本号和待保留定制清单。
3. 建立可恢复快照（例如独立分支、tag 以外的备份 commit 或经验证的源码归档），并验证快照可读。
4. 获取目标官方 Release tag 的源码与 commit SHA；不要用浮动的 `main` 代替已发布 tag。

### 5.2 三方增量集成

以“原官方基线、本地定制现状、目标官方 Release”进行三方比对。按文件和功能分类处理：

- 官方新增且本地无冲突的文件：核对依赖后纳入。
- 官方更新、本地未修改的文件：可采用官方版本。
- 官方与本地均修改的文件：逐项语义合并，保留本地功能并纳入官方修复/功能；禁止仅按行数、文件名或关键词自动选择一侧。
- 本地独有功能和生成代码：检查其 schema、路由、依赖注入、API、前端和测试接入是否完整。
- 更新前后端时，核对官方新 API 与本地 UI/接口类型是否一致。

重点审查：计费与网关行为、认证/权限、配置兼容、数据库 schema 和 migrations、依赖注入生成代码、前后端 API 契约、构建及部署配置。

### 5.3 Migration 安全

- 已经应用到任何共享/线上数据库的 migration 文件必须视为不可变：不得改文件名、内容、checksum 或编号。
- 新增 migration 使用未占用的新编号，并验证所有部署环境的执行顺序一致。
- 发现历史 migration 编号冲突时，先设计兼容策略并单独审批；不得通过重编号已应用 migration 来掩盖冲突。
- 上线前核对新旧数据库中的 migration 记录、checksum、实际 schema 和回滚影响。不能仅凭本地空库测试判定线上安全。

### 5.4 验证与版本更新

按影响范围逐级验证，至少包括：

1. 后端格式检查、定向测试、完整编译；必要时运行相关集成测试。
2. 前端类型检查、受影响功能的定向测试、生产构建和静态资源完整性检查。
3. 根 Dockerfile 正式镜像构建；核对镜像内二进制版本与镜像 tag。
4. 本地容器启动、健康检查、关键 API/界面 smoke test；涉及 migration 时使用隔离数据库验证升级路径。
5. 检查没有冲突标记、意外删除定制、凭证泄露或误改数据文件。
6. 更新上游基线记录：官方版本、tag、commit SHA、合并日期及重要冲突处理。
7. 新官方基线下的首个本地版本采用 `X.Y.Z-r1`；把该版本展示为官方基线 `X.Y.Z` 与完整构建号 `X.Y.Z-r1` 两种层级。

验证未通过时不得宣称合并完成，不得继续推送或部署；应说明失败项与未验证范围。

## 6. 推送与部署边界

- Release 检查只是 push 前的准入检查，不代表已授权合并或部署。
- 合并完成、测试通过后，是否提交/推送仍按用户的明确指示执行。
- 线上部署是独立操作，必须另行获得授权并遵守 `AGENTS.md` 的服务器、备份、数据和发布规则。
- 推送前检查发现上游有新 Release 时，用户可以选择“先合并”或“暂不合并”；未选择前保持当前代码和远端状态不变。

## 7. 建议保留的基线记录

建议在项目中以轻量、可审查的方式记录当前上游基线，至少包含：

```text
upstream_repository: Wei-Shaw/sub2api
upstream_release: vX.Y.Z
upstream_commit: <完整 commit SHA>
local_build_version: X.Y.Z-rN
integration_commit: <sshzy 仓库 commit SHA>
integrated_at: YYYY-MM-DD
```

当前仓库已选择根目录 `upstream-baseline.json` 记录可审查的官方 tag、commit 和本地构建号；本机通过 `git config core.hooksPath .githooks` 启用 `pre-push`，检查逻辑位于 `scripts/upstream_release_guard.py`。其他开发者仍须独立启用钩子。`AGENTS.md` 已补充准入与构建约束；此记录只证明基线来源，不替代三方移植、迁移或部署验证。
