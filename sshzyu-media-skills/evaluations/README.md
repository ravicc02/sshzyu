# 评估

本目录记录「这套技能按文档从头走一遍，还跑得通吗」的实跑证据，以及可从最终产物复算的检查结果。它不评价剧本写得好不好，也不把一次实跑当成内容质量证明。

## 两类证据

| 类型 | 回答的问题 | 位置 |
| --- | --- | --- |
| 回归夹具 | 录下来的那次运行，检查器与产物是否仍然一致 | 由 `tests/` 中的评估测试维护 |
| 主工作流实跑 | 换一个新项目、只给一份创意，流程本身是否可执行 | `runs/<日期>-<主题>/` |

主工作流实跑要记录的是**摩擦**，不是顺利执行的步骤：哪一步需要人工介入、哪个检查器报错、文档写的与脚本实际行为是否一致、哪个字段只能靠猜。

## 一次实跑包含什么

```text
runs/<日期>-<主题>/
├── RUN-LOG.md          # 固定提交、环境事实、阶段结果、卡点、跑偏、证据索引
├── REPORT.md           # 结论与下一轮优化清单
├── project/            # 真实项目（文档、素材、成片、交付包）
└── evidence/           # check/verify JSON、ffprobe、抽帧、SHA256、文件清单
```

大体积媒体保留在 `project/剧集/<EP>/制作成果/` 与 `export/`；证据文件记录校验值，便于确认报告引用的是哪一版产物。

## 记录规则

1. **绑定提交**：实跑开始时记录 `git rev-parse HEAD`，期间不改套件；否则问题无法归属到同一版文档与脚本。
2. **区分「已执行」与「已通过」**：命令退出 0 只说明进程结束，不说明流程正确；以检查器输出、成片实测和产物校验为准。
3. **区分「文档宣称」与「代码可执行」**：路由文字、技能存在、ZIP 能解开，都不等于生产链路已接通。
4. **如实标注未验证项**：没有真实调用的接口、没有人工看过的画面、没有跑过的发布前测试，都要写成未验证，不能用其他项代替。
5. **不美化**：卡点按严重度排序；跑偏写明是技能缺陷还是合理妥协。

## 与其他评估的区别

- `tests/` 证明脚本面对合成输入、篡改和边界条件时的行为，不证明真实流程顺畅。
- 本目录的实跑证明流程可执行性，不证明内容质量或商业可用性。
- 模型探索、供应商响应和运行状态只保留去标识后的结论；密钥、签名 URL、私有素材不得写入本目录。
