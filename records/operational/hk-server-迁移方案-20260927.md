> 修订:2026-09-27 —— **mpay 已弃用**(Ravi 已切换第三方支付),整块从迁移清单剔除。

## 2. 迁移前需确认事项

### 2.1 新机要求

- 磁盘 ≥ 40G(现机 29G 已用 85%,别再租小盘)、2C4G 起步
- 系统:Linux(建议 Ubuntu 22.04/24.04 LTS,与现机同系)
- 需安装:docker + docker compose plugin、nginx、certbot(python3-certbot-nginx)、fail2ban、rsync
- 需放行端口:22、80、443;**8080/8787/3306/5432/6379 不得对公网暴露**(沿用只绑 127.0.0.1 的设计)
- 时区核对:`timedatectl`(与旧机一致,避免日志/统计错位)

### 2.2 已拍板事项(2026-09-27)

- ~~WireGuard wg0 是否还在用~~ → 不迁(Ravi 确认无设备使用)
- ~~frps 是否带走~~ → 暂不迁(Ravi 确认;后续发现依赖再补)
- ~~mpay 是否迁移~~ → **不迁**(Ravi 确认已切第三方支付,mpay 弃用)
- ⚠️ **第三方支付回调核对**:到第三方支付平台后台确认①回调/通知 URL 指向的域名(若竟是 `pay.sshzyu.com`,该子域就得跟着处理,不能直接弃);②平台是否绑定了服务器 IP 白名单,有则先加新机 IP —— **迁移开始前必须完成**

## 3. 执行步骤

### 阶段 0:准备(不停机,提前 1 天做)

```bash
# 新机:装依赖(Ubuntu 示例)
apt update && apt install -y nginx certbot python3-certbot-nginx fail2ban rsync
curl -fsSL https://get.docker.com | sh

# 旧机 → 新机:预同步静态数据(服务照常跑)
rsync -avz --exclude='postgres_data' --exclude='redis_data' hk-server:/opt/sub2api-deploy/ root@NEW_IP:/opt/sub2api-deploy/
rsync -avz hk-server:/opt/sshzyu-docs/ root@NEW_IP:/opt/sshzyu-docs/
rsync -avz hk-server:/etc/nginx/ root@NEW_IP:/etc/nginx/
rsync -avz hk-server:/etc/letsencrypt/ root@NEW_IP:/etc/letsencrypt/

# 新机:剔除 mpay 站点(容器不迁,配置也不启用)
rm -f /etc/nginx/sites-enabled/mpay
nginx -t && systemctl reload nginx

# 新机:权限对齐、systemctl enable fail2ban
```

### 阶段 1:停机窗口(20-40 分钟,选低峰期)

```bash
# 旧机:停 sub2api 栈(只此一套)
ssh hk-server 'cd /opt/sub2api-deploy && docker compose stop'

# 旧机 → 新机:最终同步(停机状态下数据一致)
rsync -avz hk-server:/opt/sub2api-deploy/postgres_data/ root@NEW_IP:/opt/sub2api-deploy/postgres_data/   # 3.3G 主要耗时
rsync -avz hk-server:/opt/sub2api-deploy/redis_data/ root@NEW_IP:/opt/sub2api-deploy/redis_data/
rsync -avz --delete hk-server:/etc/nginx/ root@NEW_IP:/etc/nginx/
```

### 阶段 2:新机拉起并本机验证(域名未切,无公网影响)

```bash
# 新机
cd /opt/sub2api-deploy && docker compose up -d
docker compose ps   # 容器 healthy

# 验证(域名 DNS 还指旧机,用 --resolve 强制走本机)
curl --resolve sshzyu.com:443:127.0.0.1 https://sshzyu.com/health          # 期望 200
curl http://127.0.0.1:8080/health; curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8787/

# 数据完整性抽查(新旧机各跑一遍对比行数)
# docker exec sub2api-postgres psql -U <user> -d <db> -c "select count(*) from users;"
```

### 阶段 3:切 DNS(Ravi 在域名商后台操作)

1. `sshzyu.com`、`www` 的 A 记录 → 新机 IP;`pay.sshzyu.com` 的 A 记录**删除或改停用页**(确认 2.2 回调域名后操作)
2. 生效后(可用 `dig +short sshzyu.com` 确认)公网验证:主站登录、`/health`
3. 证书续期(拷贝来的证书可无缝续):新机 `certbot renew --dry-run`,通过后无需操作,到期前自动续
4. 完成一笔**小额真实充值测试**,确认第三方支付回调正常打到新机(sub2api 日志可见回调请求)

### 阶段 4:观察与回退

- 旧机**保留 3-7 天不销毁**。sub2api 容器保持停止(数据完好,随时可回退);**mpay 容器也保持停止**且不要删,观察期内万一发现第三方支付竟还依赖它,数据还在
- 回退 = 域名商后台把 A 记录改回旧机 IP + 旧机 `docker compose start`,5 分钟内恢复
- 观察期重点:sub2api 上游转发错误率、第三方支付回调日志(`docker logs sub2api-*` 里的 pay/notify 相关请求)
- 观察期满无异常 → 旧机可销毁(销毁前最后跑一次全量备份到本地 `backups/`;mpay 数据届时一并随旧机清掉,如想永久留底就先导出订单表 CSV)

## 4. 风险清单(按严重度)

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| 第三方支付回调用的是 `pay.sshzyu.com` 或绑了旧机 IP | 充值回调失败,订单状态卡住 | 迁移前到第三方平台后台核对(见 2.2)——这是现在**唯一**的支付风险点 |
| 漏迁 letsencrypt renewal 配置 | 10-27 证书到期后无法自动续期 | 整目录 rsync 含 live/archive/renewal,新机 `certbot renew --dry-run` 验证 |
| 旧机销毁过早 | 无法回退 | 强制保留 3-7 天观察期 |
| 新机防火墙忘开 80/443 | 全站不通 | 阶段 2 本机验证 + 阶段 3 公网验证双卡点 |
| frps/wireguard 有隐藏依赖 | 依赖内网穿透的服务断 | 已拍板不迁;观察期内发现异常再从旧机补迁 |
| 误把 mpay 数据当垃圾清理 | 观察期内无退路 | 旧机 mpay 容器和 volume 原样保留到观察期结束 |
